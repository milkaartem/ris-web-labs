# Отчёт по лабораторной работе №2
## Тема: «Архитектура и модель данных»

- **Дисциплина:** РИС и Web (Б1.В.ДЭ.01.02.02)
- **Вуз:** Казанский государственный энергетический университет (КГЭУ)
- **Институт:** Институт цифровых технологий и экономики (ИЦТЭ)

- **Тема №9:** «Обращения в деканат» («Электронная приёмная деканата ИЦТЭ КГЭУ»)
- **Стек семестра:** Vue 3 + ASP.NET Core + PostgreSQL

---

## 1. Цель работы
Спроектировать трёхуровневую архитектуру информационной системы, разработать реляционную модель данных сущностей и связей (ER-диаграмму), специфицировать контракт серверного REST API с разделением операций назначения и изменения статуса, а также составить трассировочную матрицу требований на основе критериев приёмки ЛР1.

---

## 2. Выполненные задачи и результаты

1. **Архитектурная схема (`docs/architecture.md`):**
   * Сформирована трёхузловая архитектурная схема взаимодействия: клиентский SPA на Vue 3 (`localhost:5173`), сервер прикладной логики на ASP.NET Core (`localhost:5000`) и реляционная СУБД PostgreSQL (`localhost:5432`).
   * Добавлена обязательная спецификация: *«архитектура web-ИС семестра»*.
   * Детально аргументировано отсутствие прямого обращения браузера к базе данных (безопасность учётных данных, ролевой контроль доступа, серверная валидация, принцип Single Source of Truth).

2. **Модель данных и нормализация (`docs/data-model.md`):**
   * Разработан словарь проекта, связывающий лекционные термины (`Ticket`, `Site`, `User`) с предметной областью темы №9 (`Appeal`, `ServiceType`, `User`).
   * Построена ER-диаграмма на языке Mermaid, определяющая ключевые сущности, первичные (PK) и внешние (FK) ключи, типы данных и мощности связей (1:N и 0..1:N).
   * Сформулировано доказательство соответствия модели 3-й нормальной форме (3НФ): название услуги хранится в справочнике ровно один раз, в обращении указывается только внешний ключ `serviceTypeId`, что исключает аномалии модификации.
   * Разграничены машинный ключ `id` и человекочитаемый номер документа `number` («ОБР-XXXX»).

3. **Контракт REST API (`docs/api-contract.md`):**
   * Специфицированы методы `GET /api/appeals`, `GET /api/appeals/{id}`, `GET /api/service-types`, `POST /api/appeals`.
   * Реализовано строгое разделение операций: назначение сотрудника вынесено в `PATCH /api/appeals/{id}/assignee`, а изменение статуса — в `PATCH /api/appeals/{id}/status`.
   * Зафиксированы 4 обязательных статуса: `New`, `InProgress`, `Closed`, `Cancelled`.
   * Исключены антипаттерны: отсутствие метода `DELETE` и глаголов вроде `/create` в адресах эндпоинтов.

4. **Матрица трассировки требований (`docs/requirements-matrix.md`):**
   * Все три обязательных критерия приёмки ЛР1 (создание объекта, назначение исполнителя, перевод в работу) сопоставлены с конкретными полями модели данных, HTTP-запросами и кодами ответов (`201 Created`, `200 OK`).
   * Составлена расширенная матрица для всех 13 функциональных требований ТЗ.

## 3. Ответы на контрольные вопросы защиты

1. **Почему название услуги/участка не хранится в каждом обращении?**  
   *Ответ:* Согласно требованиям 3-й нормальной формы (3НФ), сущность `Appeal` должна содержать только числовой внешний ключ `service_type_id`. Название услуги хранится один раз в справочнике `service_types`. Это предотвращает избыточность хранения и аномалии обновления: при переименовании услуги в деканате достаточно обновить одну строку в справочнике, не затрагивая тысячи исторических обращений.

2. **Чем `id` отличается от `number`?**  
   *Ответ:* `id` — это внутренний машинный первичный ключ (суррогатный integer), оптимизированный для индексов БД, связей внешних ключей и параметров REST API (например, `/api/appeals/12`). Поле `number` — это бизнес-номер документа для человека (например, `ОБР-2026-0012`), предназначенный для отображения в интерфейсе, печати и устного диалога студента с деканатом.

3. **Почему назначение и смена статуса — разные PATCH?**  
   *Ответ:* Это разные бизнес-действия с принципиально разграниченными зонами ответственности и правами доступа. Назначение исполнителя (`PATCH .../assignee`) выполняет заместитель декана, при этом статус обращения не меняется (остаётся `New`). Смену статуса (`PATCH .../status`) выполняет назначенный сотрудник при взятии в работу (`InProgress`) или завершении (`Closed`). Единый эндпоинт создал бы риск случайной перезаписи полей и сломал бы ролевую валидацию.

4. **Почему браузер не пишет в PostgreSQL напрямую?**  
   *Ответ:* Браузер — недоверенная клиентская среда, работающая на устройстве пользователя. Прямой доступ потребовал бы передавать пароль от СУБД в клиентский код, что приведёт к полной компрометации данных. Кроме того, база данных не может самостоятельно проверять сложную ролевую логику приложения. Сервер ASP.NET Core выступает централизованным валидатором и контроллером доступа (Single Source of Truth).
