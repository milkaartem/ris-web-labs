## 1. Цель работы
Спроектировать и создать реляционную схему базы данных в PostgreSQL (`db/schema.sql`), согласованную со словарём и сущностями проекта, наполнить её учебными данными во всех четырёх статусах (`db/seed.sql`) и выполнить обязательные SQL-запросы (`db/queries.sql`): фильтрацию с сортировкой, `JOIN` со справочником, сводку `GROUP BY` и проверку ограничения `CHECK`.

## 2. Реализованные SQL-скрипты

1. **`db/schema.sql`** — пересоздание (`DROP TABLE IF EXISTS ...`) и создание трёх таблиц в `snake_case`:
   * `service_types` — справочник категорий услуг деканата (`id` PK, `name` UNIQUE, `description`, `is_active`);
   * `users` — пользователи системы (`id` PK, `full_name`, `email` UNIQUE, `role` с `CHECK` на `'Student' | 'ViceDean' | 'Staff'`, `created_at`);
   * `appeals` — главный объект (`id` PK, `number` UNIQUE, `title` 5–80 симв., `description` 10–500 симв., `service_type_id` FK, `status` с `CHECK (status IN ('New', 'InProgress', 'Closed', 'Cancelled'))`, `created_at`, `updated_at`, `created_by_user_id` FK, `assignee_user_id` FK `NULL`).
   * Созданы индексы с комментариями: `appeals_status_idx`, `appeals_service_type_id_idx`, `appeals_created_at_idx`.

2. **`db/seed.sql`** — наполнение учебной базы `course_appeals`:
   * 4 категории услуг деканата (`service_types`);
   * 4 пользователя с ролями `Student`, `Staff`, `ViceDean` (`users`);
   * 5 обращений во всех четырёх статусах (`New`, `InProgress`, `Closed`, `Cancelled`), включая обращения без назначенного исполнителя (`assignee_user_id IS NULL`), а также выравнивание последовательностей `setval(...)`.

3. **`db/queries.sql`** — обязательные запросы:
   * Фильтрация и сортировка: `WHERE status = 'New' ORDER BY created_at DESC`.
   * Соединение `JOIN`: выборка обращений с названием услуги (`service_types.name`) и ФИО автора/исполнителя (`users.full_name`).
   * Агрегация `GROUP BY`: подсчёт количества обращений в каждом из четырёх статусов (`COUNT(*)`).
   * Заготовка проверки `CHECK`: попытка вставки статуса `'Done'` (отклоняется СУБД по ограничению `appeals_status_check`).

## 5. Ответы на контрольные вопросы защиты

1. **Зачем нужен индекс по статусу?**  
   *Ответ:* Список обращений чаще всего фильтруют по конкретному статусу (например, `WHERE status = 'New'`) или строят по нему сводку `GROUP BY status`. Индекс `appeals_status_idx` позволяет PostgreSQL быстро находить нужные строки без полного сканирования всей таблицы (`Seq Scan`).

2. **Почему название услуги не хранят текстом в заявке/обращении?**  
   *Ответ:* По требованиям 3-й нормальной формы (3НФ) текстовое название услуги хранится ровно один раз в таблице-справочнике `service_types`, а в таблице `appeals` хранится только числовой внешний ключ `service_type_id`. Это исключает дублирование строк и гарантирует, что при переименовании услуги достаточно изменить одну запись в справочнике.

3. **Чем `JOIN` отличается от `GROUP BY`?**  
   *Ответ:* `JOIN` соединяет строки разных таблиц по общему ключу (например, подставляет к обращению название услуги из `service_types` и имя автора из `users`), не уменьшая детализацию строк. `GROUP BY` объединяет множество строк с одинаковым значением поля (например, по `status`) в одну итоговую группу для вычисления агрегатов (`COUNT(*)`, сводка для руководителя).
